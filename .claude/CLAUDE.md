# WHY

anyhost keeps every Claude Code and Codex session of every machine the Architect works on in Cloudflare R2, lists every session on every machine, and resumes a session on any machine from R2 alone, so a dead or busy machine never holds his history hostage.

# Facts

- The repository root is a cmod mod: `src/mod.ts` is the `defineMod`, `hooks/register.ts` only registers it, and `tests/` holds its `bun test` suite. `node_modules/@cmodjs/core/docs/` is the cmod documentation for the installed version.
- `cli/` is the `anyhost` program, TypeScript on Bun with its own `package.json`, `bun.lock` and `tsconfig.json`. `bun run --cwd cli build` compiles `cli/dist/anyhost-<os>-<arch>` with `bun build --compile` for each machine in `CMOD_MACHINES`, or all four, as cmod builds its own program, and runs `bun install` first. `bun run --cwd cli check` type-checks it. Both run `bun run --cwd relay build` first, which writes `relay/dist/relay.js`, the relay that `cli/src/connect.ts` carries as text and uploads, so a bare `bun test` fails before one of them ran. `cli/src/embedded.d.ts` types the files the program carries as text, the relay bundle, the Herdr pane and its icons, as TypeScript 7.0 has no type for an import `with { type: 'text' }`, which bun-types gives from TypeScript 7.1 on, when that file goes. `bun test` at the root runs the mod's tests, `cli/tests/` and `relay/relay.test.ts`, while `cmod check .` runs `tests/mod.test.ts` and `relay/relay.test.ts` and no file of `cli/tests/`, so CI runs `bun run --cwd cli test` beside it, which builds the relay and runs each file of `cli/tests/` in a worker of its own (`bun test --parallel`), its tests one after another. A file holds the tests of one Capability, so the slowest file sets the suite's time, and helpers a test machine needs live in `cli/tests/program.ts`. `bun test --concurrent` runs no file here: Bun refuses `onTestFinished`, which every test machine's cleanup uses, in a concurrent test, and the tests of a file share `process.env` and the clock.
- `package.json` `cmod.program` names `anyhost`, and `cli/package.json` names `bun run build` as its build, so `cmod publish` attaches `anyhost-<os>-<arch>` for darwin and linux on arm64 and x64 to each GitHub release, `cmod install` downloads it, and `cmod link` builds it from the checkout.
- No file holds a comment: the oxlint rule `anyhost/no-comments` (`lint/comments.js`, a JS plugin `.oxlintrc.json` loads, which `cmod check` runs) refuses every one but a `@ts-`, `oxlint-` or `eslint-` directive and `/// <reference`. Names say what code does, tests say what it must do, and a fact the code cannot show goes here.
- The program reads its version from `.claude-plugin/plugin.json` at build time, so a release raises only that file's `version`.
- A push to `main` runs `.github/workflows/ci.yml`, which tests on `macos-latest` and `ubuntu-latest` and, once both passed and the tag `v<version>` is missing, runs `cmod publish` on macOS. `docs/releasing.md` holds the steps.
- The program is the only code that talks to the relay. Its socket and object routes go through `cli/src/relay.ts` alone, which compiles against `relay/protocol.ts`, while `/v1/health` and `/v1/join`, which take no device token, go from `cli/src/connect.ts` too, and `/v1/health` from `cli/src/doctor.ts` while no program answers. The socket's connect and each object route carry `X-Anyhost-Version`, the program's version from `.claude-plugin/plugin.json`. Each program process, the service and each command, keeps one WebSocket to the Pool: it pings every 30 seconds (`PING_MS`, in `relay/protocol.ts`) whatever the socket carries, counts 40 seconds (`PONG_MS`) with nothing heard while a ping waits as a drop, and opens again at once, then after 1, 2, 4 and up to 60 seconds. A WebSocket carries its messages in order, so a pong comes behind every answer the Pool sent before it, and every message heard starts the 40 seconds again: a seal's 16 answers of about 700 KB queued on a link at 150 KB/s keep their one socket, while a link under about 420 KB/s dropped it every 70 s when only a pong counted. `Relay.run` packs ops into requests of up to `MAX_OPS` and `MAX_MESSAGE_BYTES`, sends a put over 1 MiB as `PUT /v1/objects/<key>` beside them, and reads a get the answer had no room for with `GET /v1/objects/<key>`, which goes on with `Range` from the byte a broken download reached. A request with no answer goes again on the next socket, whole, so every op of the Pool answers a repeat as it answered the first run. A socket that brings no answer for 40 seconds (`ANSWER_MS`) while a request sent on it waits drops first, as the Pool answers pings without waking, and each answer starts the 40 seconds again, so a slow link that keeps answering keeps its socket, and a pong or another machine's message never counts as an answer. Cloudflare keeps listing a sleeping machine's half-open socket until a message sent on it fails, so the Pool counts a socket alive only while the last message it heard on it, which it keeps in memory, its last ping, which the platform records without waking the Pool (`getWebSocketAutoResponseTimestamp`), or its connect is within `LIVE_MS` (45 s, in `relay/protocol.ts`): only a live socket gets a message, `devices` answers `connected` from it, the clone check at a join and a connect counts only a live socket, and a routed message for a machine with no live socket answers `offline`. Cloudflare takes the whole Pool out of memory once no event ran in it for a short while, a message still on its way included, which forgets the message times, so `LIVE_MS` holds for the pings alone: a ping waits up to 10.49 s behind 1 MiB of uploads at 100 KB/s, so two reach the Pool at most 40.49 s apart, and 4.51 s is left for the link's own delay. A ping sent more than 34.51 s (`LATE_PING_MS` in `relay.ts`, `LIVE_MS` less 10.49 s) after the last one, as after the machine slept with its socket open, may reach the Pool after it counted the socket not live, when a take's `released` went only into `waiting`, and an idle machine's pings never wake the Pool to send it again. So a socket whose last ping is that old carries nothing more: its next ping, request or message opens a new socket instead (`isLate`), whose welcome carries the `released` before anything goes up, as the timers of a machine that wakes fire in the order they came due, a drain's before the pinger's. A request that socket never sent goes on the next one with the rest. That check reads the wall clock, which counts the time a machine slept, as Linux's monotonic clock does not. `reconnect` closes the socket open on the last login, as a join replaces the device token the object routes check. Past the Free plan's 100,000 Worker requests a day Cloudflare answers 429 `error code: 1027` until 00:00 UTC, which `/status` names, and `anyhost doctor` with no program running, both through `isDailyLimit` in `relay.ts`. The `claims` op takes a `prefix` and reads only the rows under it. Cloudflare's Free plan gives the Pool's SQLite 5,000,000 rows read a day: on 2026-11-11 a list that read every claim, 19,400 rows for 9,700 claims, from the Herdr pane's two views every 30 s, read 2.8 million rows in an hour and refused every op from 16:49 UTC, so no list reads the claims table. Every write of a claim raises the counter `meta.changed`, stamps the row's `changed` with it and sends `claimed` with that number to every live socket, `forget` empties a row's `device` the same way, which only its holder may send, and the welcome carries the counter. Each process keeps the holders in `anyhost.db`'s `holders` with the last number in `holders_changed` (`followHolders` in `claims.ts`), applies a `claimed` whose number is one past its own, and on a skipped number, a welcome with another counter or its first read asks `changes` since its number, which answers only later rows by the `claims_by_changed` index, as Kubernetes resumes a watch from a `resourceVersion` and lists again after 410 Gone. The Pool logs every statement that reads over 100 rows (`HEAVY_ROWS`). A put whose condition failed while the object's etag is the md5 of its own bytes counts as written. The service waits out an outage; a command fails its requests once a connect fails, with the relay's address and the reason.
- The relay's address is `url` in `relay.json` in the state folder, and the device token the cmod secret `token` (`cmod secret get anyhost token`). `relayLogin` reads both at the first connect and again at a connect after relay.json's modified time or size moved, since each `cmod secret get` starts a process and a service whose relay does not answer connects every minute. So a machine joined while the service runs connects within a minute, and at once when the service itself joined. `saveRelayLogin` in `device.ts` alone writes them, the token first, so the write of relay.json says a new token is there. With neither, the service keeps its queue and uploads nothing, its `/status` says the machine is not joined, and every command fails saying so. A `cmod secret get` that fails, or a relay.json the program cannot read, is no answer: the relay state is `offline` with the reason, and the next connect reads the login again. A close with 4401 or 4403 is the relay's final answer for that login, so `forgetRelayLogin` deletes relay.json and then the token with `cmod secret delete`, unless relay.json's write moved since `relayLogin` read the refused login, as a newer join's does. It runs in turn with `saveRelayLogin` within one process, and the next connect waits for it. So `anyhost join` posts the link to the program's `/join` when a program answers at `serveSocket()`, and joins in its own process only when none does, as then no forget runs. Tests and test machines use the test relay `anyhost-test-relay`, bound to the bucket `anyhost-test`, never `anyhost`: `serve(device, names, cloudflare)` takes the Worker and bucket that Connect Cloudflare and relay updates use, and the Cloudflare they and every join reach, which only a test passes: `cli/tests/connect.test.ts` runs the program from a script that sends each Cloudflare call and `cf` run to its stand-in.
- The option `join` holds the link `cmod install heyJordanParker/anyhost --option 'join=<link>'` set. The service reads the options as it starts, before its watcher is ready, and joins with the link, and again within a minute of `cmod option anyhost join <link>`, at its next options read, then empties it with `cmod option anyhost join ""` whether the relay took it or not. `join` takes a link alone or inside the install command. `/status`'s `joining` is `running` from the program's start until its first options read found no link, and while a join runs, and `failed` with the reason until the machine joins or the relay welcomes it, which the Step and `anyhost doctor` show with their fix: the program never tries that link again, and only a new invite joins.
- Every join in the service, with an invite or the setup code, sends the machine the service connects as, from `ANYHOST_DEVICE_*`, so a machine renamed since the service started joins under the name its socket uses, as the Pool refuses another name of a connected id as a clone. `anyhost join` and `anyhost connect` with no program answering send `cmod device --json`'s.
- Connect Cloudflare uploads the relay into an account that holds no Worker, then turns its workers.dev route on. On an account that holds the Worker, it turns the route on first and reads its `/v1/health`, so `turnOn` runs once either way. A route that was off answered Cloudflare's own 404 page (`text/html; charset=UTF-8`, `<!DOCTYPE html>…`) 13 ms after the call that turned it on returned, and the relay 0.55 s and 1.4 s after it in two live runs, so that read asks again every second while the page answers, for up to 30 s (`ROUTE_LIMIT_MS`), and then fails naming the limit. An account that refuses the read of the Worker's settings with 403, as one where the person has no Workers access, is left out of the setup and the update with a line, and every other failure, a 5xx too, fails them. Every setup and update line goes through `login.say`: the Step's lines for Connect Cloudflare, the program's log for `updateRelay`.
- The Worker checks the setup code against its own `SETUP_CODE_SHA256` and passes it to `Pool.join`, which keeps every other rule of a join.
