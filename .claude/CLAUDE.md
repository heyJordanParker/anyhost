# WHY

anyhost keeps every Claude Code and Codex session of every machine the Architect works on in Cloudflare R2, lists every session on every machine, and resumes a session on any machine from R2 alone, so a dead or busy machine never holds his history hostage.

# Facts

- The repository root is a cmod mod: `src/mod.ts` is the `defineMod`, `hooks/register.ts` only registers it, and `tests/` holds its `bun test` suite. `node_modules/@cmodjs/core/docs/` is the cmod documentation for the installed version.

- The program is the only code that talks to the relay. Each program process, the service, each job and each command, keeps one WebSocket to the Pool: it pings every 30 seconds (`PING_MS`, in `relay/protocol.ts`) whatever the socket carries, counts 40 seconds (`PONG_MS`) with nothing heard while a ping waits as a drop, and opens again at once, then after 1, 2, 4 and up to 60 seconds. A WebSocket carries its messages in order, so a pong comes behind every answer the Pool sent before it, and every message heard starts the 40 seconds again, so answers queued on a slow link keep their socket. `Relay.run` packs ops into requests of up to `MAX_OPS` and `MAX_MESSAGE_BYTES`, sends a put over 1 MiB as `PUT /v1/objects/<key>` beside them, and reads a get the answer had no room for with `GET /v1/objects/<key>`, which goes on with `Range` from the byte a broken download reached. A request with no answer goes again on the next socket, whole, so every op of the Pool answers a repeat as it answered the first run. A socket that brings no answer for 40 seconds (`ANSWER_MS`) while a request sent on it waits drops first, as the Pool answers pings without waking, and each answer starts the 40 seconds again, so a slow link that keeps answering keeps its socket, and a pong or another machine's message never counts as an answer. Cloudflare keeps listing a sleeping machine's half-open socket until a message sent on it fails, so the Pool counts a socket alive only while the last message it heard on it, which it keeps in memory, its last ping, which the platform records without waking the Pool (`getWebSocketAutoResponseTimestamp`), or its connect is within `LIVE_MS` (45 s, in `relay/protocol.ts`): only a live socket gets a message, `devices` answers `connected` from it, the clone check at a join and a connect counts only a live socket, and a routed message for a machine with no live socket answers `offline`. Cloudflare takes the whole Pool out of memory once no event ran in it for a short while, a message still on its way included, which forgets the message times, so `LIVE_MS` holds for the pings alone: a ping waits up to 10.49 s behind 1 MiB of uploads at 100 KB/s, so two reach the Pool at most 40.49 s apart, and 4.51 s is left for the link's own delay. A ping sent more than 34.51 s (`LATE_PING_MS` in `relay.ts`, `LIVE_MS` less 10.49 s) after the last one, as after the machine slept with its socket open, may reach the Pool after it counted the socket not live, when a take's `released` went only into `waiting`, and an idle machine's pings never wake the Pool to send it again. So a socket whose last ping is that old carries nothing more: its next ping, request or message opens a new socket instead (`isLate`), whose welcome carries the `released` before anything goes up, as the timers of a machine that wakes fire in the order they came due, a drain's before the pinger's. A request that socket never sent goes on the next one with the rest. That check reads the wall clock, which counts the time a machine slept, as Linux's monotonic clock does not. `reconnect` closes the socket open on the last login, as a join replaces the device token the object routes check. Past the Free plan's 100,000 Worker requests a day Cloudflare answers 429 `error code: 1027` until 00:00 UTC, which `/status` names, and `anyhost doctor` with no program running, both through `isDailyLimit` in `relay.ts`. The `claims` op takes a `prefix` and reads only the rows under it. Cloudflare's Free plan gives the Pool's SQLite 5,000,000 rows read a day, so no list reads the claims table. Every write of a claim raises the counter `meta.changed`, stamps the row's `changed` with it and sends `claimed` with that number to every live socket, `forget` empties a row's `device` the same way, which only its holder may send, and the welcome carries the counter. Each process keeps the holders in `anyhost.db`'s `holders` with the last number in `holders_changed` (`followHolders` in `claims.ts`), applies a `claimed` whose number is one past its own, and on a skipped number, a welcome with another counter or its first read asks `changes` since its number, which answers only later rows by the `claims_by_changed` index. The Pool logs every statement that reads over 100 rows (`HEAVY_ROWS`). A put whose condition failed while the object's etag is the md5 of its own bytes counts as written.
