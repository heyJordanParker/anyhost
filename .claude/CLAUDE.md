# WHY

anyhost keeps every Claude Code and Codex session of every machine the Architect works on in Cloudflare R2, lists every session on every machine, and resumes a session on any machine from R2 alone, so a dead or busy machine never holds his history hostage.

# Facts

- The repository root is a cmod mod: `src/mod.ts` is the `defineMod`, `hooks/register.ts` only registers it, and `tests/` holds its `bun test` suite. `node_modules/@cmodjs/core/docs/` is the cmod documentation for the installed version.
- `cli/` is the `anyhost` program, TypeScript on Bun with its own `package.json`, `bun.lock` and `tsconfig.json`. `bun run --cwd cli build` compiles `cli/dist/anyhost-<os>-<arch>` with `bun build --compile` for each machine in `CMOD_MACHINES`, or all four, as cmod builds its own program, and runs `bun install` first. `bun run --cwd cli check` type-checks it. Both run `bun run --cwd relay build` first, which writes `relay/dist/relay.js`, the relay that `cli/src/connect.ts` carries as text and uploads, so a bare `bun test` fails before one of them ran. `bun test` at the root runs the mod's tests and `cli/tests/`, while `cmod check .` runs only the mod's.
- `package.json` `cmod.program` names `anyhost`, and `cli/package.json` names `bun run build` as its build, so `cmod publish` attaches `anyhost-<os>-<arch>` for darwin and linux on arm64 and x64 to each GitHub release, `cmod install` downloads it, and `cmod link` builds it from the checkout.
- The program reads its version from `.claude-plugin/plugin.json` at build time, so a release raises only that file's `version`.
- A push to `main` runs `.github/workflows/ci.yml`, which tests and, when the tag `v<version>` is missing, runs `cmod publish`. `docs/releasing.md` holds the steps.
- The program is the only code that talks to the relay. Its socket and object routes go through `cli/src/relay.ts` alone, which compiles against `relay/protocol.ts`, while `/v1/health` and `/v1/join`, which take no device token, go from `cli/src/connect.ts` too, and `/v1/health` from `cli/src/doctor.ts` while no program answers. Each program process, the service and each command, keeps one WebSocket to the Pool: it pings every 30 seconds, counts a pong more than 40 seconds late as a drop, and opens again at once, then after 1, 2, 4 and up to 60 seconds. `Relay.run` packs ops into requests of up to `MAX_OPS` and `MAX_MESSAGE_BYTES`, sends a put over 1 MiB as `PUT /v1/objects/<key>` beside them, and reads a get the answer had no room for with `GET /v1/objects/<key>`, which goes on with `Range` from the byte a broken download reached. A request with no answer goes again on the next socket, and one unanswered 40 seconds (`ANSWER_MS`) drops its socket first, as the Pool answers pings without waking. `reconnect` closes the socket open on the last login, as a join replaces the device token the object routes check. Past the Free plan's 100,000 Worker requests a day Cloudflare answers 429 `error code: 1027` until 00:00 UTC, which `/status` names. The `claims` op takes a `prefix` and reads only the rows under it. A put whose condition failed while the object's etag is the md5 of its own bytes counts as written. The service waits out an outage; a command fails its requests once a connect fails, with the relay's address and the reason.
- The relay's address is `url` in `relay.json` in the state folder, and the device token the cmod secret `token` (`cmod secret get anyhost token`). `relayLogin` reads both at the first connect and again at a connect after relay.json's modified time or size moved, since each `cmod secret get` starts a process and a service whose relay does not answer connects every minute. So a machine joined while the service runs connects within a minute, and at once when the service itself joined. `saveRelayLogin` in `device.ts` alone writes them, the token first, so the write of relay.json says a new token is there. With neither, the service keeps its queue and uploads nothing, its `/status` says the machine is not joined, and every command fails saying so. A close with 4401 or 4403 is the relay's final answer for that login, so `forgetRelayLogin` deletes relay.json and then the token with `cmod secret delete`, unless relay.json's write moved since `relayLogin` read the refused login, as a newer join's does. It runs in turn with `saveRelayLogin` within one process, and the next connect waits for it. So `anyhost join` posts the link to the program's `/join` when a program answers at `serveSocket()`, and joins in its own process only when none does, as then no forget runs. Tests and test machines use the test relay `anyhost-test-relay`, bound to the bucket `anyhost-test`, never `anyhost`: `serve(device, names)` takes the Worker and bucket that Connect Cloudflare and relay updates use, which only a test passes.
- The option `join` holds the link `cmod install heyJordanParker/anyhost --option 'join=<link>'` set. The service joins with it at its start and within a minute of `cmod option anyhost join <link>`, at its next options read, then empties it with `cmod option anyhost join ""` whether the relay took it or not. `join` takes a link alone or inside the install command.
- The service listens on the unix socket `serve.sock` in the state folder (`serveSocket()` in `serve.ts`) and prints `unix:<path>` as its first line, which cmod's `program` job reads, so no web page and no other user reaches it. The mod reaches it only there: GET `/status`, `/claims/<session>` and `/machines`, and POST of JSON to `/connect`, `/connect/account`, `/connect/r2`, `/join`, `/machines/invite`, `/machines/remove`, `/move` and `/move/keep`. `anyhost doctor`, `anyhost attach`, `anyhost move` and `anyhost join` reach it at the same path. `/status` carries the Connect Cloudflare the Step started, whose lines and question the Step shows. macOS refuses a unix socket path over 104 bytes, so a scratch `XDG_STATE_HOME` on a Mac stays short, such as under `/tmp`.
- A second `anyhost serve` whose `serve.sock` answers `/status` exits 1 naming the program that answers, because two programs on one state folder would both write its database. It removes only a socket file nothing answers on. A POST whose body is no JSON answers 400 with the reason.
- `anyhost attach <session>` (`attach.ts`) always opens a WebSocket at the service's `/attach`, on the machine that runs the session too, so every viewer shares that machine's one `claude attach`: two `claude attach` clients draw at the size of the latest and break the other's screen (worker-spec W9). Its text messages are the attach it sends, `{"t":"localNetwork","problem"}` after each direct dial, and the routed messages about its stream that come back, and its binary messages are the stream's frames. The service shows a session this machine holds itself, as it shows a viewer on another machine, sends any other attach on its one relay socket, and answers `invalid` with the reason for a session no machine holds. While the relay does not answer, it shows a session whose record in `sessions/` says it runs in this machine's background, and answers `offline` for any other. After the stream's `moved` frame it sends an attach of a new stream, which its program sends where the claims say the session is now, and its stream starts over from byte 0 (`Stream.startOver`), taking nothing until the new host's `start`, so the keys typed meanwhile reach the new host. After a `detach` or `offline`, `anyhost attach` sends the same attach again after 1, 2, 4 and up to 60 seconds, and ends at the host's `exit` frame or when its terminal's input ends. As it ends, it turns off the terminal modes Claude Code set (the alternate screen, the hidden cursor, the modes 2004, 2031, 1004, 1000, 1002, 1003 and 1006 that Claude Code's daemon records for a session in `~/.claude/daemon/roster.json`, the kitty keyboard flags and modifyOtherKeys), because a viewer whose session ended on the host never sees Claude Code turn them off.
- In Claude Code 2.1.318, `←` in `claude attach` turns the process into Claude Code's agents view (`claude agents`) in its working folder, which asks to trust a folder it does not know, and the process ends once the person leaves that view. So the host runs `claude attach` in the session's folder, and when it ends while the session runs, the host starts it again with the same id at the viewers' size, which paints the whole screen for every viewer. The session's record in `sessions/<pid>.json`, with its pid alive (`recordedSessions` in `background.ts`), says it runs, and a background session's only while Claude Code's daemon runs: `claude stop` ends the attach by itself after removing the record, and so does Claude Code killing a session whose attach stalled 5 s, which it respawns at most 6 s later, as it respawns a crashed one 10 s later. So an end with no signal reads the records at once and, when the record is gone, follows them for 10 s (`RESPAWN_MS`), starts the attach again once the record is back, and ends every viewer with the stopped message when it is not, also 10 s after a `claude stop`. A respawned session's process wrote its record 12.5 s after a crash at a Mac load average of 250, and 41 s after a stalled attach at 257, where viewers still read it stopped. During a crash respawn the attach goes on, and `claude agents --json` lists the session with no `pid`. systemd stopping `anyhost-claude.slice` signals the attach, the daemon and the session in the same moment, and Claude Code removed the record 0.35 to 0.53 s after the attach ended on anyhost-d, so an end by a signal, as also the OOM killer or a `kill -9` gives, follows the records for 3 s (`STOPPING_MS`), reads them once more, and ends every viewer with `The session <id> stopped running on <machine>.` once the record or the daemon goes. After 3 ends in a row each within 2 s of its start, it ends every viewer with the reason.
- Claude Code 2.1.319 runs one daemon per machine, `claude daemon run --origin transient`, which runs every background session as processes of its own, and the first `claude --bg` or `claude attach` that finds none starts it in that client's cgroup, while `claude agents --json` starts none. Its lock `~/.claude/daemon.lock` (in `CLAUDE_CONFIG_DIR` when set) names its `pid` and, on Linux, its `procStart`, field 22 of `/proc/<pid>/stat`, and it removes the lock as it ends. Its socket is `/tmp/cc-daemon-<uid>/<first 8 hex of the sha256 of Claude Code's folder>/control.sock`. It ends itself once nothing holds it, 50 s after its start when no client came. A `claude attach` whose daemon went, or any other Claude Code client, starts a new daemon, 163 ms to 4 s later on anyhost-d, which adopts every session whose process still runs (`bg adopt` in `~/.claude/daemon.log`) under its own id, with no copy under a new one: Claude Code's own recovery. A daemon that starts about 60 s after a crash finds them reaped. So on Linux the program runs each `claude --bg` in a scope `anyhost-bg-<random>.scope` and each `claude attach` in a scope `anyhost-attach-<first 8>-<random>.scope`, both with `--slice anyhost-claude.slice`, which systemd nests under `anyhost.slice` for the dash in its name. Whichever of them starts the daemon, the daemon and its sessions live in that client's scope in the slice, outside the anyhost service's cgroup, and `systemctl --user stop anyhost-claude.slice` ends every daemon, session and attach anyhost started in the same moment, and every viewer with the stopped message. Each scope's name is new, because systemd frees a name only once it unloads the unit, which waits for every process in it, such as a daemon its client started or a session that outlived its daemon. No attach is bound to another unit, so a crashed daemon's attaches start the daemon that adopts its sessions. None of it is a service, because a `transient` daemon watches its own program file and at each Claude Code update starts its successor, as its child in the same scope, and then exits, so a unit that ended with the daemon would kill the successor and every session. A daemon started outside anyhost, as by `claude --bg` in a shell, and every daemon on macOS live outside the slice. `claude daemon stop` stops no daemon a client started, and `claude daemon stop --any` does and ends its sessions: anyhost's attaches started a new daemon 1.43 s later on anyhost-d, which ran no session, as `--any` leaves them `stopped`, and ended itself 50 s later. The host closes its `claude attach` once the record of a session it found recorded is gone and does not come back within 10 s (`keepsRunning`), as Claude Code writes it again when it respawns the session, ending every viewer with `The session <id> stopped running on <machine>.` A stopped program closes every `claude attach` it runs at SIGTERM, SIGINT or SIGHUP, as Bun's terminal gives them no controlling terminal and their scope outlives the service.
- `claude --bg --resume <id>` starts a copy under a new id (`--fork-session`) once Claude Code has a background job of that session, even a stopped one, as after a reboot, and `claude attach <id>` starts a stopped job again under its own id. `claude agents --json --all` lists the stopped, done and failed background sessions too, so the host attaches any session listed there and runs `claude --bg --resume` only for one Claude Code never ran in the background here.
- A move (`move.ts`) runs in the program of the machine that runs the session, which `/move <machine>` and `anyhost move` ask with POST `/move`, because only that program holds the session's upload queue. It waits for Claude Code's record of the session to say `idle`, drains the session with `UploadQueue.flush`, reads its working folder's code once more and drains that, seals the journal, writes the index and sends `move`. A seal short of the journal's end heals the journal as the backup's seal does, drains it and seals again, and one still short fails the move, so no machine restores a session with a hole in it. Its `step` (`waiting`, `uploading`, `moving`, `moved`, `failed`) and `line` are in `/claims/<session>`'s `move`, kept in the program's memory only: the mod refuses each prompt while the move runs, and its toast and `anyhost move` read it once a second. The machine it goes to stops a copy it runs, runs `restore()` with `take`, trusts the folder the session continues in when the `move` message's `trusted` says the first machine's Claude Code trusts the session's folder, reopens its own kept job with `claude attach`, else runs `claude --bg --resume`, and answers `moved` once Claude Code's record of the session in `sessions/<pid>.json` names a live process, within 60 s. Then the first machine stops the copy Claude Code's record names at that moment: a background copy with `claude stop`, after its viewers got the stream's `moved` frame, which makes `anyhost attach` attach again on a new stream. An interactive copy in the herdr pane `herdr agent list` names by `agent_session.value` gets SIGTERM, and `herdr pane run` types `anyhost attach <first 8>` into that pane, with the herdr on the PATH of the person's shell. Any other copy stays open. Only then is the step `moved`, and a copy that fails to stop ends the move `failed` with the reason. A session whose journal stopped during the upload, as another machine took it, ends the move `failed` and stays with that machine. Once `move` was sent, `offline`, `moved` with an `error`, the other machine's socket closing, read from `devices` every 10 s, and Keep it here (POST `/move/keep`, which works until the other machine answers) each take the claim back with `claim {take: true}` and capture the session here again.
- `claude --bg` ignores `--session-id` and prints `backgrounded · <first 8>`, which `receiveStart` reads the new session from. It refuses, with `Workspace not trusted`, a folder Claude Code does not trust there. Claude Code 2.1.319 trusts a folder whose `projects[<folder>].hasTrustDialogAccepted` in `.claude.json` (in `CLAUDE_CONFIG_DIR`, else the home folder) is true for the root of its repository's main checkout, or for the folder itself or any folder above it up to its own checkout's root, or outside git up to `/`, and has no command that sets trust. So `move` and `start` carry `trusted`, and the receiving machine writes that key for the folder's checkout root, or the folder outside git, under Claude Code's own lock of the file, the folder `.claude.json.lock` as proper-lockfile makes it, beside the path Claude Code names the config by even when that is a symlink, and renames a new file over the file the config resolves to, so a symlinked config stays a symlink.
- `jobs/<8 hex>/state.json` is the record of a job one machine's Claude Code daemon ran, with that machine's `cwd`, so anyhost never captures it, and `restore()` skips the ones earlier versions uploaded.
- The service starts `claude --bg` and `claude attach` with the person's own environment, because Claude Code's one daemon runs every background session with the environment of the process that started it first, and cmod gives a service a fixed `PATH` without the person's folders. - The stream (`stream.ts`) numbers each direction's bytes, acknowledges what it took 1 s after the first frame it has not acknowledged, with no timer while it takes nothing, as each wakeup of a viewed busy session's ends cost 2 to 15 ms of Bun's CPU, keeps up to 8 MiB its peer did not acknowledge, and on each new link sends `start` (its first link) or `ack` with what it holds, then every frame not acknowledged. A side that receives `start` after taking the peer's bytes starts over, as after the host's program restarted. Over the relay, the host sends output at most once per 20 ms, and over a direct connection or its own unix socket at once.
- The direct path (`direct.ts`): the host binds, and offers in `attached`, only its Tailscale addresses (`100.64.0.0/10`, `fd7a:115c:a1e0::/48`) and the private IPv4 addresses (`10/8`, `172.16/12`, `192.168/16`) of interfaces other than `docker*`, `br-*`, `veth*` and macOS's `bridge100` and up, which carry OrbStack's machines and Docker networks on a Mac, on the port `direct.json` in the state folder keeps, picked free at the first start. The host logs `A viewer of <session> reaches <machine> directly at <address>.` and the end of each connection.
- macOS decides a dial to a local network address by the Local Network access of the terminal app that started the process tree, and refuses it with `EHOSTUNREACH` or `ECONNREFUSED`, while Apple's own programs, such as `/usr/bin/nc`, reach the address regardless (worker-spec W6). A tmux or herdr server keeps the access of the terminal app that started it. Tailscale addresses are no local network.
- The host runs one `claude attach` per session under `Bun.Terminal` at the smallest size of its linked viewers, and resizes with SIGWINCH itself. A new viewer of a session already shown gets `CSI ?1049h` when the alternate screen is on, because a redraw sets every other mode again, then a redraw: a row less until Claude Code's output clears the screen (`CSI 2J`), or 2 seconds, then back, because 1 of 7 redraws with the size back after a fixed 300 ms painted nothing. A viewer whose link dropped keeps its stream for 60 seconds, and the next attach with its stream id goes on from the bytes each side holds. The host reads the records (`recordedSessions`) as it starts showing a session and 200 ms after each change in `sessions/` under Claude Code's folder, where Claude Code rewrites a session's record once at each change of its status, and runs no `claude agents`, which prints the same `status` from the same records at 468 times the CPU, 0.74 to 4.59 s a run on test machines. It sends each change of the record's `status` (`busy`, `waiting` at a permission prompt, `idle`), which `anyhost attach` reports to herdr in a herdr pane as `working`, `blocked` and `idle`. The record has no `state`, and the `state` `claude agents --json` adds is no fit: a session that waits for its first prompt is `blocked` there, and one whose turn ended `done`, which `herdr pane report-agent` refuses. The host starts a session it holds that Claude Code never ran in the background here with `claude --bg --resume <id>` in the folder its `sessions` row names, once Claude Code's daemon runs. The service runs Claude Code as `CLAUDE_CODE_EXECPATH`, which cmod sets, else `claude` on `PATH`.
- `anyhost.db` keeps the bucket the relay's welcome names, and a welcome that names another drops its tables and the state folder's `code/`, because journal ends and uploaded code parts belong to one bucket. `anyhost serve` then exits, and its service starts it on the new bucket.
- The relay closes a refused socket with a code: 4401 for an unknown token and 4403 for a removed machine, after which the program forgets the login and the relay state is `unjoined` with the refusal as its message, as on a machine that never joined, until it reads a login again, and 4409, the state `refused`, for a machine whose id another name holds connected, as a clone's original does. The program captures nothing in either, and its `/claims/<session>` answer carries the reason, with `cloneFixFor` from `relay/protocol.ts` for a clone, which the mod shows as an error toast once a session. - A write gets 120 seconds and as long again as its bytes take at 100 KB/s, since a 50 MB frame outlived 120 s on a Mac whose uploads moved at 0.4 to 0.9 MB/s. The limit stays total, because Bun never ends an upload that stopped moving. A download that moves no byte for 30 seconds goes on in its next try.
- The mod runs `anyhost serve` as an `isService` program job with `device.read()` in `ANYHOST_DEVICE_*`: cmod makes it a launchd agent on macOS or a systemd user service on Linux, which starts at login with no Claude Code open. The service's environment is `HOME`, `XDG_DATA_HOME`, `CLAUDE_CONFIG_DIR`, a fixed `PATH` and the job's `environment`, never the shell's or Claude Code's, so the program reads every setting from cmod options, not the environment. - A session is every file `transcript.ts` `ownerOf` names for it: Claude Code's transcript, everything under `projects/<folder>/<session>/`, `file-history/<session>/`, `tasks/<session>/` and `tasks/session-<8 hex>/`, `session-env/<session>/`, background output at `<temp root>/<folder>/<session>/tasks/*.output`, the plans its transcripts name in `planFilePath`, the `paste-cache/<hash>.txt` its history lines name, and its lines of `history.jsonl`; Codex's rollout, its lines of `history.jsonl` and `session_index.jsonl`, and its `state_5.sqlite` `threads` row as JSON. The 8 hex digits of `tasks/session-*` are the session id's first 8.
- A session's journal is records `{"device","path","at","size","after"}` plus `size` bytes: the file at `path` becomes its first `at` bytes plus the record's. `at` and the journal's sizes count the journal's bytes, and `after` is the size and sha256 of the file as its writer had it, which differ from the journal's after a restore rewrote another machine's paths. A record whose `path` ends in `/` holds that working folder's code header from `code.ts`, and one at `anyhost:code/<session>/parts/<sha256>` a part the header names, which no machine holds as a file. A record whose `after` is null, with `at` and `size` 0, says its writer's file is gone: the program writes one when the watcher or the backup's sweep finds a file it captured gone, never for a lines file or Codex's database, and replay removes the file until a later record brings it back. Each upload is one independent zstd frame at `journals/<session>/hot/<start>.zst`, written with If-None-Match.
- The journal is the chain of frames from byte 0, each starting where the one before it ends. A frame off the chain is one its writer put up while an earlier position failed: a restore skips it and ends at the first position no frame holds, its writer's next upload writes over it, and a seal deletes it once it starts before the journal's end. `chainOf` reads frames of up to 1 MiB together in one request, and a larger one by HTTP, at most 16 requests ahead, for a restore and for a seal, since a session at `uploadEvery` 0 has a frame per line, and a seal that fetched 1110 frames at once held every connection, so every upload on the machine timed out connecting once a minute.
- The program captures a session once the watcher, or a listing in its place, names one of its files while the program runs, every file from byte 0, and never reads old, unchanged files. A lines file (`history.jsonl`, `session_index.jsonl`) names the sessions of the lines past its offset in the `line_offsets` table, which starts at the file's end on the first start. Historic sessions reach R2 through a one-time import outside anyhost.
- The upload queue in `serve.ts` drains every `uploadEvery` seconds, or on each write at `0`, with one upload in flight per session. A drain is one request of every queued session's frames, after each session read what its files gained, and the first drain of each session since the program started claims it in that request, before its frames, so a takeover tells this machine. The queue drains only while the relay is connected, and at its welcome. At `0` a failed upload tries again after 1 second, then twice as long each time up to a minute. The program reads `uploadEvery` from `cmod options anyhost --json`, because one program serves every session and a service keeps the environment it started with. One `cmod options` of cmod 5.13.0 runs `claude plugin list` and a git for each project that has an `options.json`, 0.48 to 0.53 s of CPU on the Architect's Mac, so `personOptions` runs it at the start and again only once Claude Code's settings.json, where cmod keeps the options, changed its modified time or size, which the service checks every 60 seconds. Its stat follows the symlink of a settings.json in a dotfiles checkout, where a watch of `~/.claude` hears no write. An option the person never set is absent there, and the program uses `5`, as the mod's default says: replayed from the Architect's Mac's transcripts of 2026-10-06 to 2026-11-05, every write takes 1,258,076 uploads, past R2's free 1,000,000 Class A requests a month, and 5 seconds 411,952.
- After an upload that changed a session's files, `captureCode` reads its working folder in the background: one read per session, none while the last read's records still go up, and one more once they are up when the session changed meanwhile. The code goes up in later drains than the files, every part before the header that names it, and a part stays in `codeWaiting` until R2 has it, because `captureCode` counts every part it returned as written. At `uploadEvery` 0 a drain that carries a file's change carries no code, and a drain of code puts up to `CODE_PIECES` (4) frames of at most `CODE_PIECE_BYTES` (128 KiB) at once, and the journal counts them up to the first that failed. From a test machine whose link takes about 1.2 MB/s, 16 MiB of code catches up in 31 to 45 s, against 86 s one 256 KiB piece at a time, and a line still reaches R2 in about 1 s while the session's repository commits. 8 pieces at once fill that link, and lines wait past 2 s. At N seconds a drain carries all the code waiting. A working folder missing on this machine gets one log line and no code, and the session's files still go up.
- Every 60 seconds the program stats the files of the sessions written in the last 10 minutes (`QUIET_MS`), and at its start and once an hour (`SWEEP_ALL_MS`) every file of every session it captures, queues the ones whose size or modified time moved, writes `index.json` when it changed, and seals each session quiet for 10 minutes. The full sweep finds the writes no event named, such as an inotify overflow, an FSEvents drop or a write while the program was down, as Syncthing pairs its watcher with an hourly rescan, so a quiet session costs no stat in the other minutes.
